SpiderHeck PeerJS / WebRTC Network Bench

Standalone multiplayer network diagnostics. This page does not load Unity or modify game state. Run it in two browsers/devices to test the signaling server, ICE/STUN/TURN candidate gathering, WebRTC data channel, latency, and message-size limits.

School Wi-Fi test: use HTTPS or localhost, keep this tab open and in the foreground, and run the bench once on school Wi-Fi and once on a phone hotspot. A second browser/device on a different network is needed for the peer-to-peer test. The report never stores raw IP addresses or ICE candidate lines. PeerJS's public signaling and the configured STUN/TURN services are contacted when you run tests.

1. Local browser and ICE checks

The game-matching profile uses Google's public STUN servers and PeerJS's shared public TURN service. STUN-only is a diagnostic comparison; it will fail on networks that require a relay.

    Test summary

    Run local checks or connect two browsers to begin.

    Interpretation: no server-reflexive candidate often means STUN traffic is blocked or DNS/UDP is restricted. Relay candidates indicate TURN was reachable. A successful selected relay pair proves relay connectivity for that pair. “Signaling open” only proves PeerJS could reach its signaling service; it does not prove WebRTC can connect.

    How to run a useful school Wi-Fi test
    
    
      
      
    1. Open this same page on two devices/browsers. Keep one on school Wi-Fi; put the other on a phone hotspot or another internet connection. A second tab on the same laptop is only a basic smoke test, not a NAT/firewall test.
      2. 
      
    2. On both devices, use the same ICE profile and enter a useful network label. Run browser + ICE gathering checks and save each JSON report.
      3. 
      
    3. On the first device, click Host and share its generated peer ID. On the second device, enter that ID and click Join.
      4. 
      
    4. After the data channel opens, click Run binary data-channel size test on either side. Save both reports, including any errors and the selected candidate-pair type/protocol.
      5. 
      
    5. Repeat both tests using the Google-STUN-only profile, then compare school Wi-Fi results against the phone hotspot. Do not post reports publicly if you added identifying network labels.
      6. 
    
    
    
    Candidate gathering is a diagnostic, not a guarantee that the same candidate pair can connect to another player. The actual selected pair and echo test are the connectivity checks. Browser policy, PeerJS cloud outages, school firewall rules, and service-side rate limits can affect results. The game itself and NGO scene recovery are not exercised here.
